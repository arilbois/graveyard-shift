# Technical direction

- Host: Kiro IDE, targeting the compatible VS Code Extension API, not private Kiro internals.
- Extension host: TypeScript + Node runtime. Webview: React + TypeScript + Vite, loaded as packaged local assets. Use modern bundling and small runtime footprint.
- Test: Vitest for pure logic, fast-check for property-based tests, VS Code extension integration tests for host behavior; lint and typecheck are required.
- State: deterministic and independently testable session engine, reminder scheduler and companion state machine. UI must not own business timing logic.
- Clock: inject a clock for tests; correctly handle focus changes, idle, sleep, system time changes, restart and workspace changes.
- Signals: activity/focus/editor events are estimates, not direct measurements of effort or health. Document change events may be generated by agents; do not count all changes as human typing.
- Persistence: store settings in VS Code workspace/user configuration as appropriate; state/history via extension globalState or globalStorageUri. No remote telemetry or content exfiltration.
- Security: strict Content-Security-Policy in every Webview, use `asWebviewUri` for local assets, validate all messages across extension/webview boundary, avoid inline script and unrestricted resource loading.
- Accessibility: keyboard operable, screen-reader labels, respects prefers-reduced-motion, sufficient contrast, sound always user controllable.
- Never use unsupported DOM manipulation to inject overlays into Kiro. An editor-area Webview is permitted; OS-wide fullscreen requires a separate app and is outside MVP.
- Avoid premature services, databases, analytics SDKs, complex state libraries or AI inference. No unlicensed artwork, sounds, or fonts.
- Do not push to a remote, publish, install untrusted tools, or change licenses without user approval.
